## Commit 1 — LoRA Inference Validity Boundary

**Repository:** yakobd/The_Sales_Agent_Evaluation_Bench
**File:** model_card.md — Limitations section

**Before:** A vague flag stating evaluation used system-prompt
simulation rather than real LoRA weights, with no explanation
of why this matters or how much it matters.

**After:** A technically grounded validity boundary statement
explaining that system-prompt simulation modifies input
activations while LoRA adapter inference modifies weight
matrices (W_eff = W₀ + (α/r)·B@A). For the four rule-based
rubric dimensions (banned phrases, ICP fingerprints, timezone
tokens, honesty flags), the two approaches produce equivalent
scores because these dimensions are sensitive to string
presence not token-distribution shape. For the tone-marker
dimension (LLM sub-judge), distributional differences may
produce divergent scores. Delta A should be read as valid for
the four rule-based dimensions and an unvalidated proxy for
tone — unlikely to differ by more than the tone-marker
dimension's weight (estimated ≤15% of overall score).

**Why this matters for an FDE hiring manager:** The original
limitation implied the evaluation was flawed without explaining
the boundary. The new version shows the engineer understands
exactly what was measured, what it is valid for, and what
remains unvalidated. This is the difference between flagging
a problem and understanding it.

## Commit 2 — Reasoning Token Cost Accounting

**Repository:** yakobd/The-Conversion-Engine
**File:** agent/act4_mechanism.py — get_mechanism_metadata()

**Before:** additional_cost_usd: 0.0 — implying the
confidence-aware abstention mechanism added zero marginal
cost beyond the base model call.

**After:** A reasoning_token_note field explaining that
additional_cost_usd measures extra LLM calls (correctly zero)
but does not account for reasoning tokens generated by the
thinking model. The confidence-aware abstention prefix caused
96.9% reasoning tokens across 30 held-out simulations — a
32:1 reasoning-to-answer ratio. Reasoning tokens are billed
at output token rates. Total mechanism cost equals base model
cost multiplied by approximately 32x output multiplier when
run on a thinking model. Audit instructions provided via
usage.completion_tokens_details.reasoning_tokens.

**Why this matters for an FDE hiring manager:** The original
metadata would cause any engineer reusing this mechanism to
severely underestimate its cost when deployed on a thinking
model. The new version provides the information needed to
budget correctly and audit accurately. Cost transparency is
a production engineering requirement.

## Commit 3 — Augmentation Diversity Gradient Explanation

**Repository:** yakobd/The_Sales_Agent_Evaluation_Bench
**File:** datasheet.md — Known Issues section

**Before:** A bare flag stating "94.3% of training pairs are
augmented variations of 128 originals. Diversity is lower than
2,541 independently authored pairs would provide." No
explanation of why this is a problem at the gradient level.

**After:** A mechanically grounded explanation of the gradient
dynamics: near-duplicate examples produce highly aligned
gradient signals that push LoRA A and B matrices in similar
directions repeatedly, causing loss to fall quickly on
recurring token patterns (openers, CTA phrasings, sentence
shells) rather than generalizable style policy. Two concrete
diagnostics provided: grouped holdout split (all augmentations
from one original must stay in the same split — sharp
performance drop indicates memorization) and gradient norm
comparison by module (attention vs MLP pressure identifies
whether training concentrated in phrase-shaping layers).
Delta A should be read as improvement on the measured
distribution pending grouped holdout validation.

**Why this matters for an FDE hiring manager:** The original
flag identified a risk without explaining its mechanism or
providing a way to test whether it materialized. The new
version gives the next engineer who uses this dataset the
tools to validate whether the training generalized or
memorized — a concrete quality improvement to the dataset
documentation.

## Commit 4 — LLM Judge Bias Audit Status

**Repository:** yakobd/The_Sales_Agent_Evaluation_Bench
**File:** model_card.md — Evaluation Results section

**Before:** Inter-rater agreement reported (≥80%, overall 93%)
with no mention of position bias, length bias, or
self-preference bias testing. Delta A = +0.263 (p<0.0001)
presented without bias audit caveat.

**After:** A Judge Bias Audit Status section covering all
three known LLM-as-a-judge biases. Position bias: unknown —
presentation order was not randomized, position-swap audit
not yet run. Length bias: partially screened — negative
length-score correlation found in deterministic artifacts,
live LLM judge not separately audited. Self-preference bias:
partially mitigated — different Qwen model families used for
generation and judging, preventing direct self-grading but
not eliminating shared post-training style familiarity.
Conservative interpretation: Delta A is a strong result under
the current judge protocol, not a fully bias-cleared
model-quality gain. Minimum check package specified: position
swap on 20+ pairs, length-score correlation, lineage
separation confirmation.

**Why this matters for an FDE hiring manager:** The original
model card implied the evaluation was fully validated by
inter-rater agreement alone. The new version shows the
engineer understands the difference between consistency
(what inter-rater agreement measures) and bias-freedom
(what it does not measure). This is the level of evaluation
sophistication expected in production ML systems.
